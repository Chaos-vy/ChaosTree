Why ChaosTree

Property What it means
Cache-locality first N-ary nodes pack into pre-allocated, exact-capacity arrays — up to ~40% fewer memory stalls on large range scans vs. pointer-chasing structures.
O(N) bulk loading buildFromSorted and importFlatMatrix construct trees directly from sorted data, with a tunable fill factor [0.5, 1.0].
Strictly compatible Built on JDK 21 SequencedCollection / SequencedSet / SequencedMap. Validated against 214,000+ Guava Testlib cases for exact TreeMap/TreeSet semantics.
Serializable & Cloneable Native O(N) bulk-load restoration on deserialize; full Cloneable support.
Zero dependencies Nothing else on the classpath.

Custom API surface (4 methods)
Method What it does
display() / display(Style.ASCII/UNICODE) Prints the tree structure to stdout for debugging.
importFlatMatrix(matrix, factor) N-ary only. O(N) bulk-load from a pre-sorted 2D array via arraycopy.
exportFlatMatrix() N-ary only. Serializes the tree back to a flat 2D array.
buildFromSorted(Iterator, factor) N-ary only. O(N) bulk-load from any sorted iterator.

The last 3 methods are N-ary-tree specific — Binary family trees (AVL/RBT) only expose display().

1a. Bulk Load (sorted input)

Result: importFlatMatrix at factor 0.75f is a steady ~8x faster than the JDK's own bulk loader from 10,000 keys up (6.11x at 1,000). At factor 1.0f (fully packed nodes) it is 9.7–10.7x faster from 10,000 keys up (7.93x at 1,000). Against JDK sequential put at 1,000,000 keys it is 118x faster at 0.75f (0.994 ms vs 117.514 ms) and 145x faster at 1.0f (0.808 ms vs 117.514 ms). The iterator-based bulkLoad is only 8–15% faster than TreeMap: the per-element iterator cost dominates, so the real gain comes from handing the engine a flat array.

Caveat on bulkLoad (Iterator): the small gap over TreeMap.bulkLoad (8–15%) is expected. It is what a genuine O(N) build looks like: both loaders do the same linear work, and that work is memory-bound. Every element has to be spilled out of RAM, fetched into the CPU through the iterator, and written into a node, so that fetch is the cost being measured, not the tree logic. The iteration source in these runs was also a sorted map, so the timing includes walking that map's nodes as well. Treat bulkLoad as the truthful O(N) baseline. importFlatMatrix is faster because it skips the per-element iterator entirely.
Why importFlatMatrix costs about 1 ns per key: it does not read the array element by element. It copies whole chunks of the flat array into the nodes with System.arraycopy, which the JVM compiles to a bulk memory move at JDK-intrinsic speed. There is no per-key iterator call, no comparison and no rotation, so the cost is memory bandwidth for the copy rather than per-element work. That is why it sits far below the O(N) iterator path above.

1c. Random Put (uniformly random order)

Result: B+Tree is slower than TreeMap at 1,000 (1.52x) and 10,000 (1.13x) keys, then pulls ahead at 100,000 (1.24x) and 1,000,000 (1.69x), both clear of the error bars. The 1,000,000 figure reproduces: an independent 25-warmup run measured 438.784 ms for B+Tree, within 0.5% of the 440.925 ms here. The earlier 5- and 10-warmup runs (634–662 ms) were not yet at steady state, and TreeMap is the noisier of the two at 1,000,000 (744 ms here vs 812 ms in that run).

Why random put flips at about 20,000 keys: this is not a slow design, it is a different cost model. While the data lives inside the L2 cache, a memory hop costs almost nothing and the only thing separating the two trees is the work per insert. TreeMap just links one new node. B+Tree has to shift array slots inside the leaf to keep it sorted, and with no cache misses to save, that shifting is pure extra work. Once the data starts spilling between L2 and L3, every miss costs on the order of 4–25 ns (the L1-to-L3 transition), and the layouts diverge. The per-key cost shows it: TreeMap goes 129 → 247 → 744 ns/key from 10,000 to 100,000 to 1,000,000 keys, while B+Tree goes 146 → 200 → 441 ns/key, because its wide nodes need far fewer pointer hops per lookup. The crossover sits between 10,000 and 100,000 keys; interpolating the two ratios on a log scale puts it near 20,000 keys.

Takeaway: ChaosTree's advantage is structural: when the input is sorted or can be handed over as a flat matrix, use importFlatMatrix / buildFromSorted. For unsorted single-key inserts it is competitive only at large N. As data crosses the L2/L3 cache cliff the performance gets increased.
