1. The Truth (168x Sequential / 2.07x Random)

Benchmark environment: Java 21.0.12 (OpenJDK), JMH 1.37, -Xms4g -Xmx4g -XX:+UseParallelGC -XX:+AlwaysPreTouch.
3 forks, 5 measurement iterations, 5,000,000 integer keys, single run per table.

1a. Sequential Keys (factor 0.75f)

5,000,000 Element Insertion — Sequential Key Order
Benchmark (Strategy) Complexity Score (ms/op) Allocated (Bytes/op) GC Time (ms)
B+Tree.dragonFeed (Native, factor 0.75f) O(N) 5.451 58,058,576 649
B+Tree.bulkLoad (Iterator) O(N) 41.202 58,298,864 197
JDK TreeMap.bulkLoad (SortedMap) O(N) 80.988 200,000,311 1,022
B+Tree.iterativePut (Sequential) O(N log N) 300.806 86,994,836 673
JDK TreeMap.iterativePut (Sequential) O(N log N) 917.328 200,001,987 717

Result: dragonFeed is 168x faster than standard JDK sequential insertion, 14.9x faster than the JDK's own bulk loader, and allocates 71% less heap than either JDK path.

The Mechanism: Given strictly sorted input, dragonFeed bypasses the entire tree-routing layer. It skips comparisons and rotations entirely, constructing nodes directly via chunked System.arraycopy(). That is the source of the 168x speedup—it is a data-oriented hardware bypass, not a magic iterative insert.

1b. Random-Order Keys (factor 0.75f)

Sequential keys are the happy phase for any tree structure. Every insert lands physically adjacent to the last one, perfectly accommodating the CPU's L1 cache prefetcher. Real-world entropy is rarely this forgiving. Here are the same 5,000,000 elements inserted in uniformly random order (fixed seed, same key/value pairs; bulk-loading bypasses cannot apply here).

5,000,000 Element Insertion — Random Key Order
Benchmark (Strategy) Score (ms/op) Allocated (Bytes/op) GC Time (ms)
B+Tree.randomPut 3,535.158 ± 399.494 62,784,682 620
JDK TreeMap.randomPut 7,314.133 ± 483.405 200,005,846 342

Result: Under random insertion, ChaosTree is 2.07x faster than the JDK and allocates 3.2x less heap. I am stating this plainly because showcasing only the sequential 168x best-case is marketing, not engineering. The gap narrows precisely because random insertion destroys the CPU cache-locality advantage for both structures. The massive slowdown versus the sequential run (300ms → 3,535ms) tracks entirely with L3 cache misses. The latency tax comes directly from random pointer-chasing across the heap, not allocation.

The JMH Profiler Artifact: If you read the raw JMH output, you will notice an anomaly: ChaosTree reports a higher gc.time (620ms) despite allocating 3.2x less garbage than TreeMap. I rooted this via raw -Xlog:gc logs. It is a JMH timing-window artifact. TreeMap's GC pauses happened to straddle unmeasured warmup iterations, causing JMH's secondary metric to undercount its true pause cost. A byte-for-byte log comparison of single pauses proved they are identical (~205ms to move ~645MB). The primary Score column is immune to this artifact.
