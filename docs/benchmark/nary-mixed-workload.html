N-ary Tree Mixed Workload — Mix-Ratio Sweep

This benchmark is designed to test under mixed work load. The Benchmark was performed on i5-13450HX 16 core with heap pinned -Xmx2g -Xmx2g for varying dataset sizes: 10K, 100K, 1M. JDK 21 is used for Benchmark.

  • @Warmup = 10 500ms each while 100K>= 1000ms each
  • @Measurement = 10 500ms each while 100K>= 1000ms each
  • Default GC

The benchmark uses mixed operations defined as (get%, put%, remove%). The following workload distributions are evaluated:

  • Read-dominant
    • (70, 20, 10) — 70% get, 20% put, 10% remove
    • (50, 25, 25) — 50% get, 25% put, 25% remove
  • Balanced
    • (34, 33, 33) — 34% get, 33% put, 33% remove
  • Insert-dominant
    • (10, 70, 20) — 10% get, 70% put, 20% remove
    • (20, 60, 20) — 20% get, 60% put, 20% remove
  • Remove-dominant
    • (20, 10, 70) — 20% get, 10% put, 70% remove

As I increased the dataset size by 10×, an interesting result emerged: the N-ary tree increasingly outperformed the pointer-based tree. This raises an obvious question: Why don't the lower-cost pointer swaps and insert/delete operations continue to outperform the N-ary tree?

The answer becomes apparent when the dataset grows beyond the effective cache capacity. With pointer-based trees, traversal involves following pointers to nodes that may be scattered throughout memory. As the working set grows, this pointer chasing can encounter the L2/L3 cache capacity cliff, increasing memory-stall time.

The N-ary tree takes a different approach. By storing multiple keys and child references within each node, a single cache-line or memory fetch can expose a larger portion of the tree to the CPU. This gives the hardware prefetcher more sequential data to work with, reducing the frequency of expensive memory accesses compared with chasing individual pointers.

This effect became more visible as the dataset increased by 10×. Although individual N-ary tree operations may perform more work inside a node, that additional work is largely performed on data that is already close to the CPU. The benchmark also showed lower cache-miss rates and higher IPC for the N-ary tree at larger dataset sizes, consistent with better utilization of the CPU pipeline and memory hierarchy.

In other words, the advantage is not simply about the number of pointer operations performed. Once the working set becomes large enough, memory locality and cache behavior can dominate the cost of the algorithm itself.

Conclusion & Caveat

These results show that the performance characteristics of a tree implementation are strongly dependent on both dataset size and workload composition. At smaller dataset sizes, the pointer-based TreeMap can benefit from the entire working set remaining closer to the CPU cache hierarchy, while the additional work performed inside N-ary nodes can become overhead.

As the dataset grows, however, the cost of pointer chasing becomes more significant. The N-ary implementations were able to maintain lower execution times across the larger datasets tested, with the difference becoming more pronounced at 100K and 1M elements.

The important caveat is that this should not be interpreted as a universal replacement for TreeMap. The benchmark uses a specific hardware configuration, JVM version, dataset generation, workload distribution, and implementation. In particular, the delete-heavy workload at 10K demonstrates that the N-ary implementation can lose when the dataset is small enough for pointer-based traversal to remain cache-friendly.

The result therefore highlights a more general point: asymptotic complexity alone does not determine real-world performance; memory locality, cache behavior, instruction throughput, and workload characteristics can materially change the outcome.
