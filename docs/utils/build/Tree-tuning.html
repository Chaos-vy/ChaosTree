ChaosTree: Choosing Degree, Fill Factor, and Load Path

0. Definitions

t        = degree                     (t ≥ 3)
maxKeys  = 2t - 1                     (logical)
minKeys  = t - 1
slots    = 2t                         (physical, +1 overflow slot)
keys[] / values[]  = 16 + 4 * 2t      = 8t + 16 B
child[]            = 16 + 4 * (2t+1)  = 8t + 20 B, 8 B aligned
distinct fills     = maxKeys - minKeys + 1 = t + 1

1. Choosing the degree t

1.1 Cost model

bytes/entry (leaf-only, excl. internal nodes, excl. Integers)
    = (2 * (8t + 16) + 40) / k  =  (16t + 72) / k        k = keys per leaf

put-fill : k = t,      fanout = t + 1
packed   : k = 2t - 1, fanout = 2t
levels   = 1 + ceil( log_fanout( ceil(n / k) ) )

leaf insert shift ~ (2t - 1) refs   (keys[] + values[], avg half of maxKeys each)

Checked against the 1M JOL census at t = 64: put-fill 4 levels / 248 internal, packed 3 levels / 63 internal.

1.3 Rules

t = 3, 4   : put-fill B/entry ≥ 34, no better than TreeMap's 40. Only for testing splits/merges.
read-heavy, large n        -> raise t   (fewer levels, fewer cache misses)
random-write-heavy         -> lower t   (shift per insert = 2t - 1 refs)
memory-bound               -> raise t   (B/entry ~ 16 + 72/t at k = t)
Measured at t = 64 (JMH, avgt): randomPut B+ vs TreeMap = 0.87x at 10K, 1.17x at 100K, 1.6x at 1M, 2.2x at 10M. The crossover is the write-side shift cost paying off only once the working set leaves cache.

2. Choosing the fill factor f ∈ [0.5, 1.0]

2.1 Formula (buildFromSorted)

targetKeys = max(minKeys, (int)(maxKeys * f))          applied to leaves and internal nodes
f < 0.5 or f > 1.0 -> IllegalArgumentException
tree not empty      -> IllegalStateException

2.2 Table, t = 64 (maxKeys = 127, minKeys = 63)

f targetKeys k leaf B/entry = 1096 / k inserts/leaf before first split = 127 - k
0.50 63 (= minKeys) 17.40 64
0.60 76 14.42 51
0.69 (ln 2) 87 12.60 40
0.75 95 11.54 32
0.80 101 10.85 26
0.90 114 9.61 13
1.00 127 8.63 0

2.3 Reference points

sequential put()           : k = t = 64  (JOL, 1M)  ~ f = 0.5
importFlatMatrix(.., 1.0f) : k = 127     (JOL, 1M)  = f = 1.0
random-insert steady state : k ~ ln 2 * maxKeys ~ 0.69 * 127 = 87

2.4 Rules

read-only / snapshot / rare writes      f = 1.0
append-only (writes hit the right edge) f = 1.0   (lower f only wastes slots, no leaf but the last is touched)
random inserts after load               f ~ 0.69  (matches steady-state fill, no split storm, no long-run slack)
random inserts + deletes, memory tight  f = 0.6 - 0.75
f = 0.5                                 same fill as put(); no memory or write advantage over building by insertion
JMH bulk-load numbers in this repo were taken at f = 0.75, t = 64 (k = 95). They do not describe f = 1.0.

3. importFlatMatrix(Object[][], f) vs buildFromSorted(Iterator, f)

exportFlatMatrix is not in these numbers. buildFromSorted error bars at 1M / 10M: 14.8% / 13.4%.

3.2 Cost of materializing the matrix

Object[][] from an Iterator : 2 arrays * (16 + 4n) = 8n + 32 B transient, plus one O(n) copy pass
n = 1,000,000 -> 8.0 MB

3.3 Decision

Input Use
Already Object[][] (exportFlatMatrix of another tree, snapshot) importFlatMatrix(m, f)
Iterator / stream / cursor / another Map, sorted buildFromSorted(it, f)
Iterator, and Object[][] is needed later anyway materialize once, then importFlatMatrix
Copy of an existing tree exportFlatMatrix + importFlatMatrix
Memory-constrained, n large buildFromSorted (no 8n B transient) 
break-even, materialize-then-import vs buildFromSorted:
    T_materialize(n) + T_import(n)  <  T_build(n)
measure T_materialize on your source; T_import and T_build are in 3.1.

4. Build once, no mutation, t ≥ 32

f      = 1.0
path   = importFlatMatrix(m, 1.0f)   if the source is already Object[][]
         buildFromSorted(it, 1.0f)   otherwise (no 8n B matrix copy)
levels = 1 + ceil(log_2t(ceil(n / (2t - 1))))
n_max(L levels) = (2t)^(L-1) * (2t - 1)
t n ≤ for 2 levels n ≤ for 3 levels n ≤ for 4 levels B/entry (leaf-only)
32 4,032 258,048 16,515,072 9.27
64 16,256 2,080,768 266,338,304 8.63
128 65,280 16,711,680 4,278,190,080 8.31 
n ≤ 2,080,768              t = 64
2,080,768 < n ≤ 16,711,680  t = 128   (64 needs a 4th level)
Only t = 64 has get() measurements. Sweep get at t = 64 vs 128 before treating the level count as decisive.
